# Ticket purchase E2E run

Run the Rstest + Playwright workflows against the existing preview environment:

```bash
bun run test:e2e:dev
```

`test:e2e:dev` runs SSO, native-auth workflows and then the ticket lifecycle against `https://eventoren.leonardomora.de`. `test:e2e` defaults to `https://eventoren.de` and runs SSO plus native-auth workflows, including an owned draft-event lifecycle: it is **not read-only**, although it does not start ticket lifecycle steps or open a Stripe checkout. For authorized read-only production SSO verification, run `E2E_TARGET=production bunx rstest run --config e2e/rstest.config.ts` instead. Production checkout is configured for live Stripe, so the explicit production ticket guard remains in place and refuses ticket E2E there until test-mode checkout and owned-resource cleanup are verified. `test:e2e:ticket` is an alias for the guarded development runner (including SSO), not a cleanup bypass. An explicit `E2E_BASE_URL` must match the selected target's canonical origin; the runner never points a production invocation at preview. The ticket workflow also refuses to enter a card unless Stripe's hosted checkout URL contains a `cs_test_` session identifier.

**Rollout incomplete:** a private Valibot-validated target-bound checkpoint stores the exact run marker, catalog event key/ID, observed tier key, Stripe test-session ID, order ID, IMAP UID and INBOX UIDVALIDITY, PDF filename/SHA-256 and organizer ticket ID. Each sequential step records `started` before an external effect and `completed` after its assertions. On retry, a completed checkout is skipped only with its exact saved order/session evidence; completed payment does not reenter a card, allowing delivery, PDF and capability-link assertions to resume from IMAP without persisting the link or QR code. A completed checkout without an open matching browser session cannot be paid on retry; reconcile it manually instead of creating another checkout. An interrupted event/product/publication/checkout/payment/check-in write is **not** replayed, even if a session or order ID was recorded. One `invocation.lock` covers checkpoint loading/saving, SSO and ticket execution; a surviving lock after a crash requires manual reconciliation. Legacy ticket checkpoints without step evidence remain blocked. At each invocation end, successful runs and >24h stale runs sweep the saved Stripe TEST session and app order: the admin read-only order proof must match the uniquely run-marked event/order, and the configured test Stripe account, organization, metadata, customer, sessions and payment history must agree. An open unpaid session is expired and an exactly owned subscription (if any) cancelled; Stripe charges, invoices and payment intents are never deleted. A customer is retained by default because Billing's email/provider mapping may reuse it; deletion additionally requires an independently verified retired Billing mapping and no invoice/charge/payment-intent/subscription (the optional cleanup callback is not configured by the runner). Missing evidence, credentials, account mismatch or ambiguous status keeps the checkpoint; no email-based discovery or live-mode cleanup. The IMAP scanner deletes only the exact run's confirmation in INBOX after verifying UID/UIDVALIDITY, recipient, marker, origin/link and PDF evidence; it requires UIDPLUS for exact UID EXPUNGE and checks absence. The Resend provider copy remains. The runner still exits nonzero after browser success: catalog archival and Stripe/IMAP reconciliation do not remove app paid orders/tickets, Billing order/customer mappings, PDF copies or all provider effects. Stale ticket checkpoints are retained, not age-deleted. Production remains blocked until test-only routing and exact-ownership cleanup are available end to end.

## Prerequisites

- Preview frontend, Convex functions, Stripe test credentials/webhooks, and ticket fulfillment/email delivery are operational. The test creates and publishes an event through the admin UI and makes a real sandbox charge.
- The Zitadel `contentoren` profile can resolve `testadmin` locally. Alternatively, provide both `E2E_AUTH_USERNAME` and `E2E_AUTH_PASSWORD`. The account must be able to create/publish events and have the organizer role. Organizer access alone may not grant application-admin access; if `/admin/events` redirects to `/sso`, provision the app-admin permission before running. A one-sided explicit credential configuration is rejected.
- Configure the existing Billing E2E mailbox. The IMAP user must also be a deliverable checkout recipient:

  ```dotenv
  TEST_CUSTOMER_MAILCOW_HOST=imap.example.test
  TEST_CUSTOMER_MAILCOW_IMAP_PORT=993
  TEST_CUSTOMER_MAILCOW_USER=ticket-e2e@example.test
  TEST_CUSTOMER_MAILCOW_PASS=...
  ```

  These values can be placed in ignored `.env.e2e.local` (or a file selected using `E2E_ENV_FILE`). Do not commit credentials. IMAP must offer TLS on the configured port.
- For the Stripe TEST sweep, configure `E2E_STRIPE_TEST_SECRET_KEY` (`sk_test_…` or `rk_test_…`), `E2E_STRIPE_TEST_ACCOUNT_ID` (`acct_…`), `E2E_BILLING_ORGANIZATION_ID`, `E2E_CLEANUP_CONVEX_URL` and `E2E_CLEANUP_ADMIN_TOKEN` (an app-admin bearer token). The read-only `ticketE2eOrderProofQuery` must be deployed before attempting provider cleanup. These are explicit cleanup credentials, not checkout settings; never use a live Stripe key. The sweep retains uncertain checkpoints if any are missing.
- Install Playwright Chromium for the installed package (`bunx playwright install chromium`). Install Poppler `pdftotext` and `pdftoppm`; the PDF helper rasterizes every delivered ticket and decodes its QR from the rendered image.
- Use Node 22+ and Bun 1.4+ as declared in `package.json`.

The test uses bounded waits for Stripe return/paid state and matching IMAP delivery; it does not use the development payment bypass, mock payment, synthetic email, or synthetic PDF. A fresh unauthenticated browser context opens the emailed capability link. The organizer ticket detail performs check-in once; after reload, authenticated read-only queries must correlate the decoded PDF QR, exact run-owned paid order, participant and single persisted check-in history entry. A started check-in may adopt only that proven outcome, never repeat the mutation. The duplicate step verifies that check-in is no longer offered and check-out is enabled for the persisted ticket; it does not submit a duplicate mutation or exercise camera scanning.

Run offline Node-worker helper checks with `bun run test:e2e:helpers` and type-check with `bun run typecheck`; neither requires credentials or a browser. Helper tests are excluded from the default `bun run test` and browser workflow configs. Admin-access and the full lifecycle are independent tests; the lifecycle calls one sequential file per event, product, publication, checkout, payment, delivery, PDF/QR, capability access, check-in and duplicate assertion, then records `done` before the invocation's cleanup barrier. Development sandbox results do not verify production live checkout or its email/fulfillment lifecycle.

On 2026-10-14, the guarded development paid-ticket workflow passed through real email/PDF delivery, capability access, persisted check-in and duplicate UI prevention. Its owned order/ticket/check-in graph was cleaned, but the invocation retained its completed checkpoint because a historical order did not prove run ownership. A passed workflow is not a successful historical cleanup; never weaken ownership checks or replay a purchase to clear that retained checkpoint.
