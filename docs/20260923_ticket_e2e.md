# Ticket purchase E2E

## Goal
Provide `bun run test:e2e` using Rstest's `@rstest/playwright` integration, running multiple real-browser tests covering paid-event creation, Stripe sandbox purchase, emailed ticket access and rendered PDF validation, and organizer check-in using the QR decoded from the PDF.

## Decisions
- Target the existing development/preview stack; default frontend is `https://eventoren.leonardomora.de`. Never charge live Stripe.
- Use actual checkout/payment/fulfillment, not the development billing bypass or mocked email/PDFs.
- Reuse the existing Billing E2E IMAP mailbox through local environment configuration; CI receives secrets directly. Do not require a sibling checkout at test runtime or commit secrets.
- Credentials may come from explicit E2E environment variables or the existing Zitadel CLI `testadmin` / `contentoren` profile locally.
- Retrieve the delivered email and attachments through IMAP. Open its ticket capability link in a fresh unauthenticated browser context.
- Render the actual ticket PDF, check its content, and decode its QR. Submit that code through organizer UI; no camera simulation is required. Check persisted check-in and duplicate handling.
- Use unique run identifiers and bounded condition polling rather than fixed sleeps. Test-data cleanup is permitted but not required.
- Prefer existing dependencies and application status APIs. Add an authenticated preview-only inspection seam only if an existing observable is insufficient; do not bypass lifecycle transitions.
- Keep existing Bun/Vitest tests, unrelated worktree changes, and production behavior intact. Reuse `#ui/...` components for any necessary UI change.

## Approach
Use an isolated Rstest config and E2E directory excluded from default unit test discovery. Keep runner/config/auth, email/PDF helpers, and browser workflow in separate modules. Multiple tests may exercise stages of one explicitly ordered lifecycle if supported by Rstest; otherwise use independently runnable workflow tests without implicit ordering. Prefer one paid purchase per full run. Fail clearly on missing prerequisites, without silently skipping required integration assertions.

## Current context
Rstest configuration and environment/auth helpers are in `e2e/`; workflows are in `e2e/workflows/`. The default command includes the existing SSO workflow and the ticket workflows; focused ticket and offline-helper commands are also available. Email and PDF helpers are in `e2e/mail` and `e2e/pdf`; `e2e/tsconfig.json` covers their Node-worker runtime. Run instructions are in `docs/ticket_e2e_run.md`. Ignored `.env.e2e.local` supplies the existing test mailbox. Development fulfillment is enabled for the existing test organization, whose configured tax policy is used unchanged. Testadmin has Eventoren admin and organizer roles. UI readiness markers prevent input before hydration, and manual organizer code entry uses the existing check-in action. Stripe automation explicitly selects the card option and supports the hosted German form. PDF text assertions tolerate line wrapping, and QR decoding uses the actual rendered image with a ticket-region fallback. Existing unrelated worktree changes are preserved. Production configuration is not a test target.

## Verification boundaries
- During implementation, run only focused new helper tests, targeted type/config checks and test discovery. Do not launch full E2E from implementation agents.
- All browser interaction and final end-to-end execution belong to a browser subagent.
- Verify real sandbox payment, delivered email, fresh-context access, actual PDF rasterization/QR decoding and persisted organizer check-in; report incomplete verification accurately.
